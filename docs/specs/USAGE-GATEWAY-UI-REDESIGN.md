# 用量页「网关账本」重设计（UI 方案）

> 状态：**待拍板**（2026-10-21）。设计稿：`docs/prototype/usage-gateway-redesign.html`（可直接打开，参数条可点，`?tab=&book=&drawer=1` 可深链到任一状态）。
> 上一版 `USAGE-GATEWAY-DETAIL-PLAN.md` 是工程实现方案，**UI 口径以本文为准**；数据契约与验收沿用那份，并按本文扩维度。

## 0. 上一版哪里不对

上一版把问题当成「缺数据 + 缺出口」，设计了「模型 tab 里加一个含网关开关」。三个硬伤：

1. **开关藏错地方**：数据源是页面级事实，藏在某个 tab 里 ⇒ 切走就丢。
2. **两张图并排 = 让用户自己做加法**：加完发现对不上（重复计数），信任就没了。
3. **会话 tab 留一句道歉**：点进来还是「网关一条都没有」，等于没解决。

## 1. 病灶：页面缺「账本」这个概念

客户端和网关是**两本独立记账的账**，不是「一个总量的两部分」。各自完整、互相重叠、口径不同（客户端有会话/小时，网关有账号/端点/失败）。当成一个数据源画，怎么补明细用户都会算错。

**设计原则**

1. **一个数字只属于一本账。** 占比、排行、峰值一律在单本账内算。
2. **跨账本的合计必须可审计。** 只出现在「合计 Token」，且必须能展开成算式（见 §4）。
3. **账本是视图参数，与「范围」同级。** 全局唯一，切 tab 不重置。

## 2. 信息架构

```
用量
├ 参数条   [范围: 今天 | 近7天 | 近14天 | 近30天 | 自定义]  [账本: 全部 | 客户端 | 网关]  [作用域]
├ 覆盖条   客户端 6.51M · 117 请求   网关 28.5M · 126 请求 · 429×9   覆盖 7/7 天   重叠 9 条 · 350K
└ 四视图   趋势 | 模型 | 会话 | 积分
```

### 2.1 覆盖条（新组件，常驻）

把「数据从哪来、覆盖多久、有没有缺口、重叠多少」从各图图注提到页面级一行。不随账本切换而变 —— 它描述**数据现状**，不是当前选择。

### 2.2 账本三态 × 四视图

| | 趋势 | 模型 | 会话 | 积分 |
|:--|:--|:--|:--|:--|
| **全部** | 双色堆叠柱 + `合计 ≈` 卡（可对账）+ 两个环 | 两个账本各一张表 + 每日按模型图 ×2 | 客户端排行 + 说明条（带跳转） | 余额口径四卡 + 请求口径双色柱 + 两张账本表 + 差额（见 §4.8） |
| **客户端** | 单色柱 | 客户端表 | 客户端排行（现状） | 只画客户端那本 |
| **网关** | 单色柱（靛蓝） | 网关表（含失败） | **换成按账号 / 按端点** | 只画网关那本 |

关键决策：**会话 tab 在网关账本下不是空态，而是换维度**。网关没有会话 ID，但有账号和端点 —— 那才是网关的「来源分布」。比一句「不支持」有用，也不用伪造数据。

## 3. 视觉编码：色相 = 账本，明度 = 模型

| 维度 | 编码 | 理由 |
|:--|:--|:--|
| 账本 | 色相：客户端 **青绿**（= 品牌色），网关 **靛蓝** | 扫一眼就知道属于哪本账，不靠图例 |
| 模型 | 同色相内的明度阶梯（c1→c3 / g1→g3） | 环形图里可区分，又不会被读成「另一个账本」 |
| 重叠 | **不给颜色**，只给数字（`重叠 9 条 · 350K`） | 重叠不是第三本账，画出来会被当成一个数据源 |

反例（别做）：给网关系列用斜纹/虚线 —— 深色主题的小图里看不清，且会被读成「预测值 / 缺失值」。

## 4. 重叠数据：区间 → 对账 → 点值

这是本设计要正面回答的问题。**上一版只写「可能重复计数」，等于把问题推回给用户。**

### 4.1 为什么不能估一个总数

C = 2.9M、G = 18.5M 这组数字，既可能是「完全重叠」（真值 18.5M），也可能是「完全独立」（真值 21.4M）。**从聚合值推不出重叠量** —— 任何单一数字都是猜。所以先给区间。

### 4.2 可证明的区间（不需要任何假设）

```
真值 = C + G − overlap       且  0 ≤ overlap ≤ min(C, G)
⇒   max(C, G) ≤ 真值 ≤ C + G
```

- 下限 = 两本账取大（最坏情况：客户端全走网关）
- 上限 = 直接相加（最好情况：两本账无交集）

这比 `≈` + tooltip 强得多：**区间是数学结论，不是免责声明**。

### 4.3 对账：逐条匹配，把重叠算出来

匹配键（四条同时满足才算同一条请求）：

| 条件 | 值 | 为什么 |
|:--|:--|:--|
| 模型 | 完全相同 | 不同模型不可能是同一请求 |
| 时间差 | ≤ 120 秒 | 两端都记「流结束」时刻（`StreamingLogSink::finish` / jsonl message timestamp） |
| token | prompt、completion 各相差 ≤ 1% | 两端计法可能有细微差别，但不能放大到误配 |
| 一对一 | 一条网关记录最多抵一条客户端记录 | 否则一条会被扣多次 |

**宁可少扣，不多扣**：少扣的后果是合计偏大，而「未匹配 N 条」会明确写出来；多扣的后果是凭空少算，用户永远发现不了。

### 4.4 用匹配率判定拓扑 —— 这一步才是「答案」

| 匹配率 | 结论 | 合计算式（**形态会变**） |
|:--|:--|:--|
| **< 10%** | 两本账基本独立（客户端直连上游） | `客户端 C + 网关 G − 重叠 O` |
| **> 90%** | 客户端走的正是网关（客户端 ⊆ 网关） | `网关 G + 直连客户端 U` |
| 中间 | 部分重叠（中途开网关 / 部分客户端走网关） | `客户端 C + 网关 G − 重叠 O`，并给区间 |

抽屉顶部直接给结论句，不让用户自己推。

**为什么算式要换形态**：子集关系下若仍写「相加再扣」，式子会变成 `6.51M + 28.5M − 6.16M` —— 扣掉了客户端账本的 95%，读起来像哪里错了。换成「取大再补」(`28.5M + 346K`) 才符合事实：网关已经记全了，客户端只剩没走网关的那几条。

### 4.4.1 客户端接入网关时，账本里到底会发生什么

这是本设计必须处理的主场景（P12 请求代理开启后，客户端流量全走本机网关）：

| 事实 | 对账的影响 |
|:--|:--|
| 一个客户端请求 → 网关记 1 条 + 客户端 jsonl 记 1 条 | 匹配率接近 100% ⇒ 判 `subset` |
| **两端账号可能不同**：客户端记登录账号，网关记被选中的账号（无缝切号） | ★ **账号绝不能做匹配键** —— 会把该对上的全漏掉，误判成「独立」 |
| 网关侧多出 429 / 失败条目（客户端看不到） | 网关行数 > 客户端行数，正常，不算「未匹配」异常 |
| 网关内部降级重试：1 个客户端请求 → 2 条网关日志 | 一对一匹配只吸收 1 条，剩下的是重试记录（通常 0 token） |
| 两端 token 计法可能细微不同（缓存 token 归属） | 所以容差 ±1%，不是精确相等 |
| 只代理了部分端点 / 部分模型 | 匹配率落在中间 ⇒ 判 `mixed`，给区间 |

**双信号判定（匹配率 + 配置状态）**：配置里「网关代理已开启」+ 匹配率高 ⇒ 高置信判 `subset`；配置显示未开启但匹配率高 ⇒ 更可能是**别的客户端**（Codex / Claude Code / 脚本）在跑同样模型，此时客户端账本仍独立，不能判 `subset`。单看匹配率会误判，单看配置会误判（开了不等于全量走），必须两个一起看。

### 4.5 能对账到哪（能力边界必须写在脸上）

网关日志只留最近 200 条（`log_keep`）⇒ **只有今天能逐条对账**，更早的只能日合计。

| 日志覆盖 | 合计的呈现 |
|:--|:--|
| 覆盖整个窗口 | 点值 + `已对账` 徽标 |
| 只覆盖窗口一部分 | 点值 + 区间（抽屉里写明哪段能对、哪段不能） |
| 完全不覆盖（纯历史窗口） | 只给区间，`对账` 入口置灰 + 说明 |

### 4.6 UI 落点

1. **合计卡**：主数字 `≈34.7M`，副标题就是算式（按拓扑换形态），右上角 `对账` 入口。算式直接印在卡上 —— 数字可审计，不用点进去才信。
2. **覆盖条**：`两本账重叠 9 条 · 350K` + `看对账`。
3. **对账抽屉**（右侧 452px）：结论 → 算式 → 匹配结果（含未匹配条数与 token）→ 匹配规则（**含「账号不参与匹配」的原因**）→ 覆盖范围 → 未匹配样本（前 3 条，带「为什么没对上」）。
4. **单本账时没有对账入口**：只有一本账，重叠无从谈起。
5. 设计稿用 `?case=independent|subset|mixed` 可切换三种拓扑评审（页脚有演示开关，不属于 UI）。

### 4.7 三条不许做的事

1. **不许用「平均重叠率」去估历史日** —— 那是编数据；历史只给区间。
2. **不许在模型 / 会话视图里做跨账本占比** —— 分母不同，任何百分比都是假的（这也是模型 tab 拆两张表的原因）。
3. **不许把对账结果落盘** —— 对账是视图层派生值，会随日志窗口滚动而变化；写进 `token_daily` 会让历史数字漂移。

### 4.8 积分：两个口径（余额 / 请求）

积分比 Token 多一层麻烦：**余额口径天然不重复，但拆不到来源；请求口径能拆来源，但会重复**。
两个都得给，且必须说清关系 —— 只给一个就是骗人。

| 口径 | 来源 | 是否重复 | 能否拆来源 |
|:--|:--|:--|:--|
| **余额** | 账号积分余额快照的差值 | **不重复**（余额只有一份） | 不能 |
| **请求** | 每条请求自带的 `credit`（客户端 jsonl 的 `usage.credit` / 网关的 `usage.credit`） | 会（同一请求两处各记一次） | 能（模型 / 账号 / 端点） |

页面结构（自上而下）：

1. **余额区四卡**（不随账本切换）：可用积分合计 / 区间消耗 / 区间入账 / 即将过期；
2. 一行说明：`上面四张是余额口径，天然不重复但拆不到来源；下面按请求累加，能拆来源但会重复`；
3. **每日积分消耗**：请求口径的双色堆叠（客户端 / 网关），与趋势视图同色系；
4. **两张账本表**：模型 × 积分 × 占比 × 请求（同样不相加）；
5. **两个口径的差额**：
   `余额口径 1,096.0 − 请求口径 1,034.0（客户端 182.1 + 网关 1,019.4 − 重叠 167.6）＝ 差额 62.0`
   差额 = **未归因消耗**（别的设备 / 没落本地日志的请求）。**绝不摊到任何来源上** —— 摊了就是编数据。
6. 每日积分收支（入账 / 消耗双向柱）、余额曲线、到期分布、积分流水 —— 都是余额侧的事实，不随账本变。

对账规则与 §4.3 完全一致，只是把 `promptTokens` 换成 `credit`：**credit 是更锐利的匹配键**
（`1.28` 这种小数比 token 更不易撞），所以积分侧的匹配率通常更高。

**实现前提**（两条，缺一条这个视图就是假的）：

- 客户端 jsonl **已经**带 `usage.credit`（实测本机 1316 处，形如 `"credit":1.28`）⇒ `token_stats` 要开始解析它；
- 网关 `UsageReport.credit` 已经解析出来但**没写进日志条目** ⇒ 要给 `RequestMeta` 加 `credit`（键集合测试同步）。

## 7. 边界与降级

| 情况 | 表现 |
|:--|:--|
| 网关无任何记录 | 账本控件「网关」置灰 + tooltip；覆盖条 `覆盖 0/7 天`；合计退化为客户端单值 |
| 网关有记录但窗口内为 0 | 网关账本各图空态 + 出口「看近 30 天」；**不画 0 值图** |
| 网关某日 `truncated` | 该日柱顶部加下界标记，图注说明「该日为下界」 |
| 升级过渡日（模型拆分不完整） | 图注标 `部分`，不隐藏 |
| 客户端无会话（服务器部署形态） | 会话 tab 现有「无客户端」形态不变；账本控件仍可用 |
| 对账所需日志已滚出窗口 | 只给区间，抽屉说明原因；不给假点值 |

## 9. 对数据契约的影响（给实现阶段）

- 账本=网关的**模型 / 账号 / 端点**三个维度都要按日持久化（上一版只规划了 model）。三个 map 在同一次聚合里顺手产出，**成本不变**，「按模型合计 = 网关卡」这条自洽约束仍成立。
- 端点维度只能靠落盘（环形窗口撑不起 7 天），会话 tab 的网关形态依赖它。
- **新增对账命令**：入参 = 窗口；读 `gateway_logs.json`（≤200 条）+ 窗口内客户端逐消息记录 `(ts, model, input, output)`；纯函数 `reconcile(client_rows, gateway_rows) -> ReconcileReport` 可单测。对账结果**只走命令返回，不落盘**（§4.7）。
- 「客户端账本不记失败」是事实不是缺陷：客户端表「失败」列显示 `—`，不显示 0。
- **积分请求口径的两条前提**：① `token_stats` 解析 jsonl 的 `usage.credit`；② `RequestMeta` 加 `credit`（`logging.rs` 的键集合测试要同步，否则前端类型与落盘条目会漂移）。
- **对账的匹配键可以优先用 `credit`**：它是小数（`1.28`），比 token 更不容易撞；token 作为次键做交叉校验。
