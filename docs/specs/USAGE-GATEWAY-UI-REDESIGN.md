# 用量页「网关账本」重设计（UI 方案）

> 状态：**待拍板**（2026-10-21）。设计稿：`docs/prototype/usage-gateway-redesign.html`（可直接打开，参数条可点，`?tab=&book=&drawer=1` 可深链到任一状态）。
> 上一版 `USAGE-GATEWAY-DETAIL-PLAN.md` 是工程实现方案，**UI 口径以本文为准**；数据契约与验收沿用那份，并按本文扩维度。

## 0. 上一版哪里不对

上一版把问题当成「缺数据 + 缺出口」，设计了「模型 tab 里加一个含网关开关」。三个硬伤：

1. **开关藏错地方**：数据源是页面级事实，藏在某个 tab 里 ⇒ 切走就丢。
2. **两张图并排 = 让用户自己做加法**：加完发现对不上（重复计数），信任就没了。
3. **会话 tab 留一句道歉**：点进来还是「网关一条都没有」，等于没解决。

## 1. 病灶：页面缺「账本」这个概念

客户端和网关是**两本独立记账的账**，不是「一个总量的两部分」。各自完整、互相重叠、口径不同（客户端有会话/小时，网关有账号/端点/失败）。当成一个数据源画，怎么补明细用户都会算错。

**设计原则**

1. **一个数字只属于一本账。** 占比、排行、峰值一律在单本账内算。
2. **跨账本的合计必须可审计。** 只出现在「合计 Token」，且必须能展开成算式（见 §4）。
3. **账本是视图参数，与「范围」同级。** 全局唯一，切 tab 不重置。

## 2. 信息架构

```
用量
├ 参数条   [范围: 今天 | 近7天 | 近14天 | 近30天 | 自定义]  [账本: 全部 | 客户端 | 网关]  [作用域]
├ 覆盖条   客户端 6.51M · 117 请求   网关 28.5M · 126 请求 · 429×9   覆盖 7/7 天   重叠 9 条 · 350K
└ 四视图   趋势 | 模型 | 会话 | 积分
```

### 2.1 覆盖条（新组件，常驻）

把「数据从哪来、覆盖多久、有没有缺口、重叠多少」从各图图注提到页面级一行。不随账本切换而变 —— 它描述**数据现状**，不是当前选择。

### 2.2 账本三态 × 四视图

| | 趋势 | 模型 | 会话 | 积分 |
|:--|:--|:--|:--|:--|
| **全部** | 双色堆叠柱 + `合计 ≈` 卡（可对账）+ 两个环 | 两个账本各一张表 + 每日按模型图 ×2 | 客户端排行 + 说明条（带跳转） | 余额口径四卡 + 请求口径双色柱 + 两张账本表 + 差额（见 §4.8） |
| **客户端** | 单色柱 | 客户端表 | 客户端排行（现状） | 只画客户端那本 |
| **网关** | 单色柱（靛蓝） | 网关表（含失败） | **换成按账号 / 按端点** | 只画网关那本 |

关键决策：**会话 tab 在网关账本下不是空态，而是换维度**。网关没有会话 ID，但有账号和端点 —— 那才是网关的「来源分布」。比一句「不支持」有用，也不用伪造数据。

## 3. 视觉编码：色相 = 账本，明度 = 模型

| 维度 | 编码 | 理由 |
|:--|:--|:--|
| 账本 | 色相：客户端 **青绿**（= 品牌色），网关 **靛蓝** | 扫一眼就知道属于哪本账，不靠图例 |
| 模型 | 同色相内的明度阶梯（c1→c3 / g1→g3） | 环形图里可区分，又不会被读成「另一个账本」 |
| 重叠 | **不给颜色**，只给数字（`重叠 9 条 · 350K`） | 重叠不是第三本账，画出来会被当成一个数据源 |

反例（别做）：给网关系列用斜纹/虚线 —— 深色主题的小图里看不清，且会被读成「预测值 / 缺失值」。

## 4. 重叠数据：区间 → 对账 → 点值

这是本设计要正面回答的问题。**上一版只写「可能重复计数」，等于把问题推回给用户。**

### 4.1 为什么不能估一个总数

C = 2.9M、G = 18.5M 这组数字，既可能是「完全重叠」（真值 18.5M），也可能是「完全独立」（真值 21.4M）。**从聚合值推不出重叠量** —— 任何单一数字都是猜。所以先给区间。

### 4.2 可证明的区间（不需要任何假设）

```
真值 = C + G − overlap       且  0 ≤ overlap ≤ min(C, G)
⇒   max(C, G) ≤ 真值 ≤ C + G
```

- 下限 = 两本账取大（最坏情况：客户端全走网关）
- 上限 = 直接相加（最好情况：两本账无交集）

这比 `≈` + tooltip 强得多：**区间是数学结论，不是免责声明**。

### 4.3 对账：逐条匹配，把重叠算出来

匹配键（四条同时满足才算同一条请求）：

| 条件 | 值 | 为什么 |
|:--|:--|:--|
| 模型 | 完全相同 | 不同模型不可能是同一请求 |
| 时间差 | ≤ 120 秒 | 两端都记「流结束」时刻（`StreamingLogSink::finish` / jsonl message timestamp） |
| token | prompt、completion 各相差 ≤ 1% | 两端计法可能有细微差别，但不能放大到误配 |
| 一对一 | 一条网关记录最多抵一条客户端记录 | 否则一条会被扣多次 |

**宁可少扣，不多扣**：少扣的后果是合计偏大，而「未匹配 N 条」会明确写出来；多扣的后果是凭空少算，用户永远发现不了。

### 4.4 用匹配率判定拓扑 —— 这一步才是「答案」

| 匹配率 | 结论 | 合计算式（**形态会变**） |
|:--|:--|:--|
| **< 10%** | 两本账基本独立（客户端直连上游） | `客户端 C + 网关 G − 重叠 O` |
| **> 90%** | 客户端走的正是网关（客户端 ⊆ 网关） | `网关 G + 直连客户端 U` |
| 中间 | 部分重叠（中途开网关 / 部分客户端走网关） | `客户端 C + 网关 G − 重叠 O`，并给区间 |

抽屉顶部直接给结论句，不让用户自己推。

**为什么算式要换形态**：子集关系下若仍写「相加再扣」，式子会变成 `6.51M + 28.5M − 6.16M` —— 扣掉了客户端账本的 95%，读起来像哪里错了。换成「取大再补」(`28.5M + 346K`) 才符合事实：网关已经记全了，客户端只剩没走网关的那几条。

### 4.4.1 客户端接入网关时，账本里到底会发生什么

这是本设计必须处理的主场景（P12 请求代理开启后，客户端流量全走本机网关）：

| 事实 | 对账的影响 |
|:--|:--|
| 一个客户端请求 → 网关记 1 条 + 客户端 jsonl 记 1 条 | 匹配率接近 100% ⇒ 判 `subset` |
| **两端账号可能不同**：客户端记登录账号，网关记被选中的账号（无缝切号） | ★ **账号绝不能做匹配键** —— 会把该对上的全漏掉，误判成「独立」 |
| 网关侧多出 429 / 失败条目（客户端看不到） | 网关行数 > 客户端行数，正常，不算「未匹配」异常 |
| 网关内部降级重试：1 个客户端请求 → 2 条网关日志 | 一对一匹配只吸收 1 条，剩下的是重试记录（通常 0 token） |
| 两端 token 计法可能细微不同（缓存 token 归属） | 所以容差 ±1%，不是精确相等 |
| 只代理了部分端点 / 部分模型 | 匹配率落在中间 ⇒ 判 `mixed`，给区间 |

**双信号判定（匹配率 + 配置状态）**：配置里「网关代理已开启」+ 匹配率高 ⇒ 高置信判 `subset`；配置显示未开启但匹配率高 ⇒ 更可能是**别的客户端**（Codex / Claude Code / 脚本）在跑同样模型，此时客户端账本仍独立，不能判 `subset`。单看匹配率会误判，单看配置会误判（开了不等于全量走），必须两个一起看。

### 4.5 能对账到哪（能力边界必须写在脸上）

网关日志只留最近 200 条（`log_keep`）⇒ **只有今天能逐条对账**，更早的只能日合计。

| 日志覆盖 | 合计的呈现 |
|:--|:--|
| 覆盖整个窗口 | 点值 + `已对账` 徽标 |
| 只覆盖窗口一部分 | 点值 + 区间（抽屉里写明哪段能对、哪段不能） |
| 完全不覆盖（纯历史窗口） | 只给区间，`对账` 入口置灰 + 说明 |

### 4.6 UI 落点

1. **合计卡**：主数字 `≈34.7M`，副标题就是算式（按拓扑换形态），右上角 `对账` 入口。算式直接印在卡上 —— 数字可审计，不用点进去才信。
2. **覆盖条**：`两本账重叠 9 条 · 350K` + `看对账`。
3. **对账抽屉**（右侧 452px）：结论 → 算式 → 匹配结果（含未匹配条数与 token）→ 匹配规则（**含「账号不参与匹配」的原因**）→ 覆盖范围 → 未匹配样本（前 3 条，带「为什么没对上」）。
4. **单本账时没有对账入口**：只有一本账，重叠无从谈起。
5. 设计稿用 `?case=independent|subset|mixed` 可切换三种拓扑评审（页脚有演示开关，不属于 UI）。

### 4.7 三条不许做的事

1. **不许用「平均重叠率」去估历史日** —— 那是编数据；历史只给区间。
2. **不许在模型 / 会话视图里做跨账本占比** —— 分母不同，任何百分比都是假的（这也是模型 tab 拆两张表的原因）。
3. **不许把对账结果落盘** —— 对账是视图层派生值，会随日志窗口滚动而变化；写进 `token_daily` 会让历史数字漂移。

### 4.8 积分：两个口径（余额 / 请求）

积分比 Token 多一层麻烦：**余额口径天然不重复，但拆不到来源；请求口径能拆来源，但会重复**。
两个都得给，且必须说清关系 —— 只给一个就是骗人。

| 口径 | 来源 | 是否重复 | 能否拆来源 |
|:--|:--|:--|:--|
| **余额** | 账号积分余额快照的差值 | **不重复**（余额只有一份） | 不能 |
| **请求** | 每条请求自带的 `credit`（客户端 jsonl 的 `usage.credit` / 网关的 `usage.credit`） | 会（同一请求两处各记一次） | 能（模型 / 账号 / 端点） |

页面结构（自上而下）：

1. **余额区四卡**（不随账本切换）：可用积分合计 / 区间消耗 / 区间入账 / 即将过期；
2. 一行说明：`上面四张是余额口径，天然不重复但拆不到来源；下面按请求累加，能拆来源但会重复`；
3. **每日积分消耗**：请求口径的双色堆叠（客户端 / 网关），与趋势视图同色系；
4. **两张账本表**：模型 × 积分 × 占比 × 请求（同样不相加）；
5. **两个口径的差额**：
   `余额口径 1,096.0 − 请求口径 1,034.0（客户端 182.1 + 网关 1,019.4 − 重叠 167.6）＝ 差额 62.0`
   差额 = **未归因消耗**（别的设备 / 没落本地日志的请求）。**绝不摊到任何来源上** —— 摊了就是编数据。
6. 每日积分收支（入账 / 消耗双向柱）、余额曲线、到期分布、积分流水 —— 都是余额侧的事实，不随账本变。

对账规则与 §4.3 完全一致，只是把 `promptTokens` 换成 `credit`：**credit 是更锐利的匹配键**
（`1.28` 这种小数比 token 更不易撞），所以积分侧的匹配率通常更高。

**实现前提**（两条，缺一条这个视图就是假的）：

- 客户端 jsonl **已经**带 `usage.credit`（实测本机 1316 处，形如 `"credit":1.28`）⇒ `token_stats` 要开始解析它；
- 网关 `UsageReport.credit` 已经解析出来但**没写进日志条目** ⇒ 要给 `RequestMeta` 加 `credit`（键集合测试同步）。

## 7. 边界与降级

| 情况 | 表现 |
|:--|:--|
| 网关无任何记录 | 账本控件「网关」置灰 + tooltip；覆盖条 `覆盖 0/7 天`；合计退化为客户端单值 |
| 网关有记录但窗口内为 0 | 网关账本各图空态 + 出口「看近 30 天」；**不画 0 值图** |
| 网关某日 `truncated` | 该日柱顶部加下界标记，图注说明「该日为下界」 |
| 升级过渡日（模型拆分不完整） | 图注标 `部分`，不隐藏 |
| 客户端无会话（服务器部署形态） | 会话 tab 现有「无客户端」形态不变；账本控件仍可用 |
| 对账所需日志已滚出窗口 | 只给区间，抽屉说明原因；不给假点值 |

## 9. 对数据契约的影响（给实现阶段）

- 账本=网关的**模型 / 账号 / 端点**三个维度都要按日持久化（上一版只规划了 model）。三个 map 在同一次聚合里顺手产出，**成本不变**，「按模型合计 = 网关卡」这条自洽约束仍成立。
- 端点维度只能靠落盘（环形窗口撑不起 7 天），会话 tab 的网关形态依赖它。
- **新增对账命令**：入参 = 窗口；读 `gateway_logs.json`（≤200 条）+ 窗口内客户端逐消息记录 `(ts, model, input, output)`；纯函数 `reconcile(client_rows, gateway_rows) -> ReconcileReport` 可单测。对账结果**只走命令返回，不落盘**（§4.7）。
- 「客户端账本不记失败」是事实不是缺陷：客户端表「失败」列显示 `—`，不显示 0。
- **积分请求口径的两条前提**：① `token_stats` 解析 jsonl 的 `usage.credit`；② `RequestMeta` 加 `credit`（`logging.rs` 的键集合测试要同步，否则前端类型与落盘条目会漂移）。
- **对账的匹配键可以优先用 `credit`**：它是小数（`1.28`），比 token 更不容易撞；token 作为次键做交叉校验。

## 13. 平台补齐：Trae / Qoder 的账本（2026-10-28）

第 12 节落地时账本只对 **WorkBuddy** 开放（`USAGE_PAGES[product].ledger` 另两个平台为 `false`），
原因是「网关」在三个平台上不是同一个东西。本次补齐的判据仍然是**数据**，不是习惯：

| 平台 | 客户端账 | 网关账 | 可选档 |
|:--|:--|:--|:--|
| WorkBuddy | `token_stats`（扫 jsonl，逐日/逐模型/credit） | `token_daily`（后台增量落库 90 天） | 全部 / 客户端 / 网关 |
| **Trae** | **不可得**：对话历史在 IDE 私有存储（加密 + 二进制索引），没有可解析的用量落盘 | **本次新建** `gateway_ledger` | **只有「网关」** |
| **Qoder** | `qoder_usage`（客户端会话 jsonl，按 credits） | **本次新建** `gateway_ledger`（日志里带 `credits`） | 全部 / 客户端 / 网关 |

### 13.1 后端：`crates/buddy-switch-core/src/modules/gateway_ledger.rs`

- **只读上游**：只读各自网关的请求日志（Trae = `trae/api_gateway_logs.json`，
  Qoder = `qoder/logs/gateway_requests.jsonl`，两者内容都是 JSON 数组），**不改**网关写路径；
- **水位线增量**：每轮只累加 `ts > watermark` 的新条目 —— 与 `token_daily::gateway_round`
  同一套语义（环形日志滚掉一条已记账的请求时数字不许倒退）；水位线缺失时做一次整窗**取大**播种；
- **三条维度同一水位线**：模型 / 账号 / 端点合计必须等于总量（单测 + 集成测试守）；
- **归属轴**：Trae 看行内 `variant` → `TraeVariant::region()`；Qoder 看 `region`；
  两者**缺失都落 `unlabeled` 单列一档**（并入 cn 会把国际流量记到国内账上）；
- **credit 字段**：`credit`（WB 口径）与 `credits`（Qoder 网关口径）都认；Trae 日志没有该字段
  ⇒ 账本 credit 恒 0（不知道，不是免费）；
- **后台任务**：`(Trae|Qoder, GatewayUsageRecord)` 已登记进 `background::TASKS`，
  两个宿主各起一个循环（每 2 分钟记**全部** scope —— 只记当前作用域会让切区域后的账本整段空）。

### 13.2 前端

- `USAGE_PAGES[product].ledger` 三平台均为 `true`；
- `PLATFORM_LEDGER_VALUES`：Trae 只给 `["gateway"]`。**不给「客户端」**（选了只能显示 0，
  那是把「没测到」说成「没用」），**也不给「全部」**（全部 = 客户端 ∪ 网关 = 网关，与「网关」
  逐值相同，两档并存就是死控件）；
- `LEDGER_VIEWS`：账本只出现在**消费来源拆分**的视图上（WB 四视图；Trae 趋势/模型；
  Qoder 趋势/模型/会话）。积分页在 Trae/Qoder 上是余额快照（与回看窗口无关），不渲染该控件；
- `CoverageStrip` 新增 `clientUnavailable`（客户端一项显示「不可得」而非 0）、
  `unit`（Qoder 用 credits 格式）、`showOverlap`（Trae/Qoder 没有逐条对账 ⇒ 不显示「重叠 0 条」）；
- `CreditLedgerTable.rows[].requests` 改为可选（客户端账的逐模型请求数不可得 ⇒ 渲染 `—`）；
- Qoder 的**会话视图**在「网关」账本下换成 `GatewaySourceTables`（账号 / 端点）——
  网关日志没有会话 id，摆空表比换维度更糟。

### 13.3 已知边界（写进页面的「数据来源」条，不许省略）

   不画空图，用一行字说明；

## 14. Trae 客户端账本：走「导入」而不是「内置解密」（2026-10-28）

第 13 节把 Trae 的账本限定成「只有网关一本」，理由是它的对话库不可解析。本次补上客户端
那一本，但**没有**内置解密 —— 决策依据是取证结果，不是口味。

### 14.1 为什么不能内置

实测（`%APPDATA%\<变体>\ModularData\ai-agent\database.db`，157 MB）：

| 事实 | 证据 |
|:--|:--|
| 是 **SQLCipher 加密**的 SQLite | 前 16 字节是 PBKDF2 salt、全文件熵 8.00；`ai_agent.dll` 里 `sqlcipherCodecAttach` / `PRAGMA key = ` / `rusqlite` / `sqlx` |
| 里面确有用量 | 二进制里有 `token_usage`(27) / `prompt_tokens` / `completion_tokens` / `credits`，以及 `fts_message_content` / `chat_session_goal` / `project` 等表名 |
| **key 不在磁盘** | `ModularData` 下只有 db / -wal / -shm 三件套；`PRAGMA key = ` 是运行时拼接的裸格式串 |

⇒ 要自动读，必须在产品里做两件事之一：**逆 key 派生**，或**读另一个进程的内存**。
两者都会让本工具变成「内置解密第三方客户端」的软件，且客户端大版本一升级就可能失效。
**这不是技术风险，是产品定位与合规风险。**

### 14.2 落地方案（第一版）：读用户导出的**明文副本**

> ⚠️ **2026-10-28 同日追加：这一节已被 15 节取代** —— 用户明确要求「内置解密」后，
> 工具改为**内置 SQLCipher、口令由用户输入**。本节保留，因为 15 节的两个代价
> （feature 并集、构建依赖）正是从这里的取舍推出来的。

用户自己跑一次 sqlcipher 导出（命令见界面上的「怎么导出明文副本」折叠块），
工具只读那份**明文** SQLite。好处：
- 零新依赖（`rusqlite` 的 `bundled` 标准 SQLite 就能读明文，不必换 `bundled-sqlcipher`，
  不用重编 OpenSSL，CI 矩阵不变）；
- 失败模式干净：**没导入** ≠ **导入了但这段没用量**，两者在界面上分开；
- 合规面干净：解密动作发生在用户手上，工具不持有 key。

代价是多一步手动操作，且导出后库是静止快照（要看最新数据得重新导出一次）。

### 14.3 接口

| 命令 | 路由 | 用途 |
|:--|:--|:--|
| `probe_trae_client_db` | `GET /api/trae/client-import/probe?path=` | 校验能否读（不保存） |
| `get_trae_client_db_config` | `GET /api/trae/client-import/config` | 已保存路径 + 文件是否还在 |
| `save_trae_client_db_path` | `POST /api/trae/client-import/path` | 保存 / 清除（`path: null`） |
| `get_trae_client_token_stats` | `GET /api/trae/client-usage?days=&scope=` | 聚合（与网关统计**同形**） |

配置落 `~/.buddy-switch/trae/client_import.json`（`{ path, savedAt }`）。

### 14.4 五种错误必须分开（`error.code`）

`missing`（没指定 / 文件不存在）· `not_plaintext`（还是加密的，最常见误操作）·
`unrecognized`（能打开但认不出会话结构）· `no_usage`（认出结构但没有用量字段）·
`io`。混成一个「读取失败」会让用户无从下手 —— 尤其 `not_plaintext` 是**必然**会撞上的：
多半是用户直接把加密的 `database.db` 指过来了。

### 14.5 schema 自适应（因为我们没解开过）

模块不写死表名：枚举 `sqlite_master` → `PRAGMA table_info` → 挑「含文本列且样本行里出现
`usage`/`prompt_tokens`/`input_tokens`」的表当消息表 → 时间列按 `created_at`/`create_time`/
`timestamp`/`ts` 等候选探测（值 > 1e11 视为毫秒）。认不出就返回 `unrecognized` **并回显
实际表名** —— 那份表名列表是后续适配的唯一依据。

### 14.6 「全部」档不合并统计卡

客户端库与网关日志会**双计**同一笔调用（既在客户端记录、又经网关转发）。所以 `all` 档
只用 `StackedDailyBar` 把两本账按日堆叠（看得出「谁占多少」），统计卡仍按网关口径，
并在图注里标注来源；**不做**「客户端 + 网关」的求和卡片。

## 15. 内置解密：SQLCipher 进仓（2026-10-28 同日追加）

第 14 节的结论是「不内置解密」。用户明确要求内置后，改为下面的形态。

### 15.1 做法

新增独立 crate `crates/buddy-switch-vault`，把 SQLCipher 关在里面，对外只暴露一个动作：

```rust
verify(src, passphrase) -> VaultInfo            // 校验口令（不写文件）
export_plaintext(src, passphrase, dst) -> VaultInfo   // ATTACH ... KEY '' + sqlcipher_export
```

命令 `unlock_trae_client_db(path, passphrase)`：
口令对 ⇒ 导出到 `~/.buddy-switch/trae/client_plain/database.db` 并设为数据源；
给的本来就是明文 ⇒ 直接用它（不做无谓的解密与复制）；
否则按 `wrong_key` / `not_sqlite` / `missing` 分开报错。

**口令仍然不由工具提取**：它只在内存里活到解锁那一刻，成功后立即清空，不落盘、不上传。
`helpBody` 直说「口令要从客户端进程用调试器取」——这一步有门槛，别让用户以为点两下就好。

### 15.2 两个必须知道的代价

**① Cargo 的 feature 是并集，「独立 crate」隔离不了 SQLCipher 本身。**

这一点我最初判断错了。`core` 用 `rusqlite` 的 `bundled`，`vault` 用
`bundled-sqlcipher-vendored-openssl`，Cargo 会取**并集** ⇒ 整个 workspace 的
`rusqlite` 都按 SQLCipher 编译，`session.rs` / `client_limits.rs` / `token_daily.rs`
三个既有使用点也跟着变。

- 功能上安全：不设 key 时 SQLCipher 与 SQLite 行为一致；
- 代价是真的：二进制变大、**构建要编 OpenSSL**。本机实测 `cargo check` 首次 **18 分钟**
  （vendored OpenSSL），之后有缓存就快。
- 独立 crate 仍然有价值，但价值在**代码边界**（「解密只在这里发生」）与**测试闭环**，
  不在构建隔离。别再用「独立 crate 所以没影响」这种说法。

**② 编 OpenSSL 需要 perl；Windows 上这是硬门槛。**

本机的两套 PortableGit 自带 `perl5.42.2.exe` 都跑不起来（`0xc0000135`，缺 DLL），
`openssl-src` 直接失败。最后用 **Strawberry Perl 便携版**（`.tmp/perl/perl/bin` 加进 PATH）才编过。
CI 上 GitHub 的 windows runner 自带 Strawberry Perl，通常无需额外步骤；**但本地环境要准备好**，
否则「别人拉下来编不过」。

### 15.3 验证（可闭环，不依赖真机库）

真实 Trae 库需要口令，CI 上不可能有 ⇒ 用**同一份引擎**造夹具来闭环：

| 测试 | 位置 | 断言 |
|:--|:--|:--|
| 加解密往返 | `crates/buddy-switch-vault/tests/vault_roundtrip.rs` | 加密库无明文头 → 导出 → 行数与正文逐字一致 |
| 错口令 | 同上 | `WrongKey` |
| 明文库不解密 | 同上 | `AlreadyPlaintext` |
| **端到端** | `crates/buddy-switch-core/tests/trae_vault_end_to_end.rs` | 加密库先被 `client_import` 判 `not_plaintext` → 解密 → 统计出 `212/180/32/3 条/2 模型` |
| 重复导出 | 同上 | 覆盖而非追加（总量不翻倍、体积一致） |

最后一条是刻意加的：`sqlcipher_export` 是「建表 + 灌数据」，不先删目标就会把旧内容
混进新副本 —— 这类错不会报错，只会让数字慢慢变大。

### 15.4 仍然没做的事

- **不自动取口令**（逆派生 / 读进程内存）。口令由用户提供，这是本功能与「内置逆向工具」的分界线。
- **不做增量**：每次解锁都是全量导出（157 MB 级），解锁后看到的是**导出那一刻**的快照。
