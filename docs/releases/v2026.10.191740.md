## 🐛 修复：统一网关（57892）重启后必须手动「关一下再开」

- 症状：配置里 `enabled: true`、界面开关也是绿的，但彻底退出再启动后 57892 上没有监听，`/health` 连接被拒；客户端只会一直「生成中」，网关侧一条日志都没有。
- 根因：`setup()` 只登记了网关运行时句柄，漏了「按配置拉起监听」那一段 —— 只有「保存配置」这个动作能启动它。
- 修复：启动时补齐 `apply()`，并新增跨两侧宿主（桌面端 / web 端）的回归护栏，任何一侧漏掉都会让测试变红。
- 可观测：网关页「启用统一网关」一行现在显示**真实监听状态**（监听中 / 未监听），开关是绿的但端口没人 accept 一眼可见。
- 升级后无需任何操作：配置启用即启动监听。

## ✨ Trae 1M 上下文：`/v1/models` 新增 `<模型>-max` 变体（issue #53）

- 此前反代清单只声明 200k（取客户端清单的 `context_window_size.default`），而 Max Mode 在上游是**请求级布尔字段**（`is_max_mode`），不是另一个模型名 —— 客户端里根本无从选起。
- 现在对支持 Max Mode 的模型会**紧跟**多列一条 `<模型>-max`，`context_length` 为 `1000000`；请求这条 id 时网关自动剥掉后缀、按基名发给上游并注入 `is_max_mode`。
- 支持表（与上游实证口径一致）：doubao-seed-evolving / glm-5.3 / glm-5.2 / deepseek-v4-pro(-official) / deepseek-v4-flash(-official) / kimi-k3 / minimax-m3 / qwen3.8-max / qwen-3.7-plus。
- 基础条目**不受影响**：窗口仍是上游默认值（如 200k）；不想用 1M 就继续用基名。
- 特例：`qwen3.8-max` 本身就以 `-max` 结尾（是真模型，不会被误剥），要给它开 Max Mode 写 `qwen3.8-max-max`。
- 统一入口同样适用：`trae-cn:glm-5.3-max`。
- 表外模型带 `-max` **不会**被识别（原样透传，由上游报「模型不存在」）—— 刻意如此，避免悄悄改写填错的模型名。
- 模型探测网格**不含**这些变体：`-max` 是请求开关不是独立模型，列进去只会让每个账号的探测请求凭空翻倍。

## 🔧 健康检查统一为 `/health`（`/healthz` 保留为别名）

- 四条网关此前是 3:1 分裂（WB / Qoder / 统一入口用 `/healthz`，Trae 用 `/health`），现在统一为 canonical `GET /health`。
- `/healthz` 作为**兼容别名**继续可用：两个路径由同一个处理器产出、返回体逐字相同，已写死 `/healthz` 的探活脚本不用改。
- 单一挂载点（`HEALTH_PATHS` + `health_routes`），四条网关共用；护栏要求「真发两个请求、都 200 且返回体逐字相同」。
