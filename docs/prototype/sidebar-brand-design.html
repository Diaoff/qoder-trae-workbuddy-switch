侧栏品牌块 × 顶栏平台图标：左缘「三图标」去混淆

已落地（方案 1，2026-10-22）：品牌块只留两行文字，折叠态整块隐藏，AppIconMark 已随唯一使用点删除。以下保留评审时的完整推导。

左边缘纵向排着三枚同族圆角方块图标 —— Windows 标题栏应用图标（16px，系统绘制）、顶栏平台图标（26px，唯一可交互）、侧栏品牌块应用图标（32px，纯静态块）。唯一能点的那个反而是最小的，两侧不能点的更醒目。本页给出核验后的根因、四种改法的可切换原型与落地要点。

二

根因（已逐条核验）

对 8d0433a 基准的静态复核 + 本地实测
  1. 同一张位图画了两遍，中间夹着唯一的功能性图标

    public/icon.png 与 public/icon-transparent.png 在仓库中是同一个 blob；Windows 原生标题栏一枚（bundle.icon 提供）+ 侧栏品牌块一枚（AppIconMark）取的是同一张图。不是「两个相似图标」，是同一图标出现在两处。

    证据：本地复验两者 SHA-256 均为 6c6199ff…e7bda；tauri.conf.json:17/:41-47 与 src/App.tsx:835-837。
  2. 视觉层级倒挂：可交互的更小，不可交互的更大

    顶栏作用域选择器的平台图标是 26px，侧栏品牌块的图标底是 32px 且带一层 primary 18% 底色。「能点的更小、不能点的更大」，与常规视觉层级正好相反。

    证据：src/components/shell/scope-selector.tsx:231-233（26px）vs src/App.tsx:835（32px + bg-primary/18）。
  3. 品牌块长得像控件却不能点

    侧栏品牌块是纯 <div>，既不是按钮也没有菜单。而「圆角方块图标 + 文字」在本应用里处处是控件样式（导航项、作用域触发器同款），这是「看错」最直接的诱因。

    证据：src/App.tsx:834（纯 div，无 role / 无 onClick）。
  4. 新发现：默认作用域下，顶栏与侧栏两枚图标近乎同图

    平台图标走官方资产（WorkBuddy 国内版 = workbuddy-official-icon.png，青绿猫脸），品牌块走 icon-transparent.png（同为青绿猫脸同族设计）。issue 截图是 Trae（深色机器人，两者色相反转）；而在默认的 WorkBuddy 作用域下，两枚图标几乎一模一样地叠在左缘一条竖线上 —— 混淆比截图更甚。

    证据：src/components/product-marks.tsx:20-47（两枚图标同族不同源）；上方舞台切到 WorkBuddy 国内版即可复现。
影响面：混淆落在最高频动作上（每次打开应用先在这一列找「切换平台」入口）；纯辨识度问题，不影响功能；/aggregate 裸壳整块不渲染侧栏（App.tsx:830）⇒「应用身份不依赖侧栏品牌块」已有先例，改动它有安全垫。
三

四种改法

落点均在侧栏品牌块一处，互斥；上方舞台可逐条预览效果
推荐

方案 1 · 只去掉品牌块的图标，保留两行文字 混淆根治 · 零布局风险

品牌块从「32px 图标 + 两行文字」变为「两行文字」，左缘只剩一枚图标 —— 且那枚就能点。
改动点
删 App.tsx:835-837 图标容器与 AppIconMark import；文字容器左内边距 px-1.5 → px-2.5 与导航项对齐。AppIconMark 失去全仓唯一使用点 ⇒ 按「不留死代码」约定删除（已核验仅此一处使用）。
收益
混淆源头消失；改动最小；三个平台、桌面与 WebUI 表现一致；无布局风险。
代价
品牌只剩两行纯文字；macOS 窗口无标题文字（hiddenTitle），应用身份靠这两行字承载（可接受）。
// src/App.tsx · 侧栏品牌块（834-837 改后）
<div className="flex items-center gap-2.5 px-2.5 pb-4">
  - <span className="grid size-8 shrink-0 place-items-center
  -               rounded-[10px] bg-primary/18 text-primary">
  -   <AppIconMark size={17} />
  - </span>
  <div className="min-w-0">
    /* Buddy Switch / 多平台账号管理 两行文字不变 */
  </div>
</div>

方案 2 · 图标与文字整块下移到侧栏底部 更彻底的产品选择

顶部只剩作用域选择器；品牌降到与「打赏 / 版本号」同级的弱信息区。
改动点
把 App.tsx:834-854 品牌块整体移入底部 <section>（892-900），pb-4 改为 pt-3 一类与本区块间距匹配的值；侧栏顶部改由导航承接。
收益
顶部纯功能控件；品牌层级更贴合它的实际重要性；WebUI 下保留渲染即仍有应用身份。
代价
底部由两块变三块（品牌 + 打赏 + 版本），密度上升；520px 最小窗口高下导航区仍有余量，不溢出。

方案 3 · 移到顶栏右侧（搜索框左侧） 不推荐

仅换了位置，不减混淆。
改动点
品牌块从侧栏顶部移至顶栏（搜索框与图标钮之间），侧栏顶部由导航承接。
收益
仅位置变化。
代价
应用图标与平台图标进同一行，同处一条视觉带；顶栏不可压缩部分在 720px 最小宽度下已占约 545px，再塞入品牌块会把右侧图标钮挤出视口。

方案 4 · 完全删除品牌块 不推荐

最干净，也最激进。
改动点
删除 App.tsx:832-854 整块；侧栏顶部失去 32px 起始块，需补内边距。
收益
左缘零冗余。
代价
macOS（titleBarStyle Overlay + hiddenTitle）与 WebUI 下应用没有任何可见名称 —— WebUI 的版本行同样不渲染，只剩浏览器标签页。除非产品明确放弃这两个形态的应用名，否则不单独采用。
方案改动面混淆是否消除macOS / WebUI 应用名布局风险结论
1 · 去图标留文字 App.tsx 一处 + 删 AppIconMark 根治（左缘只剩可点的那枚） 保留（两行文字） 无 推荐
2 · 品牌移底 App.tsx 一处（位置移动） 根治 + 顶部纯功能 保留（WebUI 必须保留渲染） 低（底部密度上升） 可选 · 更彻底
3 · 移顶栏右侧 侧栏 + 顶栏两处 不减（同行 + 窄窗挤压） 保留 高（图标钮被挤出） 不推荐
4 · 整块删除 App.tsx 一处 消除但过度 macOS / WebUI 无名 中（顶部需补内边距） 不推荐
四

结论与落地要点

结论：方案 1。它精确对应「图标看错」这一条病：不改变信息架构、不引入布局风险，三个平台与桌面 / WebUI 一致；顺带按约定清理 AppIconMark 死代码。若产品上认为这两行品牌文字放在顶部本身价值有限，方案 2 是更彻底的选择 —— 顶部只留功能控件，品牌降到它应有的弱信息级别，代价是底部密度上升。方案 3、4 不推荐（理由见卡片与上表）。

  1. 改实现：src/App.tsx:832-854 品牌块（方案 1：删 835-837 图标容器与 import，文字容器 px-1.5 → px-2.5）；product-marks.tsx 的 AppIconMark 随之删除。
  2. 同步基准原型：buddy-switch-prototype.html:1583-1591 的 .brand 标记与 demo.css:136-149 样式，避免实现与原型漂移；docs/README.md 已先行登记本页。
  3. 门禁：npm run build（tsc + 6 项契约检查）不覆盖侧栏品牌的 DOM 结构，不存在同步改动点，应保持全绿。
  4. 真机确认：macOS 需截图确认 hiddenTitle 下去掉图标后不出现「顶部一片空白」的观感（应用名只剩侧栏两行文字）。
