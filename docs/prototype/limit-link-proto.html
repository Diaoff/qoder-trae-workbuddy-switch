      限流探测

      账号 × 模型 实探 来源：账号页触发 · 未回填

      3 账号 · 3 模型可测

      可用 模型限流 账号限流 积分不足（非限流） 未实测 被动已知（台账／真实流量）
      实测是「真发一次最小请求」，会消耗极少积分并在上游留痕。 尚未运行

      ① 数据怎么同步（没有第三份数据）

      • 探测作业：model_probe 的**单作业槽**（`probe_status` 快照）。两处读同一份，按 scope 收窄。
      • 客户端台账：client_limits（只读扫 jsonl）。账号页自己刷新；网关页只取其中 active 的格当「被动底色」。
      • 池冷却：status.modelCoolings（真实流量打出来的）。网关页显示，账号页不重复展示。
      • 任一侧发起 → 另一侧下次读到的就是它；不存在「两处各自维护一份、必然漂移」。

      ② 入口与代价

      • 卡头「实测 N 格」= 台账里 仍受限 + 状态未知 的账号集合 × 模型集合（已恢复的不测 —— 日志已经证明它好了）。后端按账号为外层展开笛卡尔积，故 3 账号 × 2 模型 = 6 格；按钮上的数就是真实格数。
      • 行尾「实测」= 只打这一格；关联不到账号/模型的行置灰，`title` 写明原因。
      • 两处都 adopt:false：账号页是查证，不写池冷却。要回填请到网关页（那里有明示开关）。
      • 作业位单例 ⇒ 正在探测时按钮变进度条，重复点击不再起第二个作业。

      ③ 冲突：并列，不覆盖

      • 台账「仍受限」+ 实测「可用」⇒ 行内写 实测可用（台账仍受限），台账徽章不动。
      • 理由：台账是历史证据，实测是此刻证据；谁对不该由 UI 单方面裁定。
      • 只有「模型限流 / 账号限流 / 模型封禁」算限流；402 积分不足 与 登录失效 分列（踩过的坑）。
      • 实测独有（台账无记录）的格单列在卡尾，不伪装成台账条目。
